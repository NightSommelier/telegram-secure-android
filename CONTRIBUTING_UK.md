# Керівництво для контриб'юторів Telegram Fork-Secure

> [!NOTE]
> [The English version of this documentation is available in CONTRIBUTING.md](CONTRIBUTING.md).

## Межі архітектури та точки входу

Цей репозиторій містить активну кодову базу проєкту Telegram Android Fork-Secure. Усі зміни повинні вноситися виключно сюди.

Перед початком роботи ознайомтеся з картою коду:
- Ознайомтеся з [`docs/TELEGRAM-ANDROID-FORK-MAP_UK.md`](docs/TELEGRAM-ANDROID-FORK-MAP_UK.md) для визначення відповідального модуля.
- Криптографічні операції, ратчет, сховища та серіалізацію зберігайте в модулі `SecureOverlay/`; не виносьте логіку протоколу в класи відтворення інтерфейсу (UI).
- Будь-яка зміна повинна дотримуватися принципу **fail-closed**: пошкоджені носії, некоректні стани чи непідтримувані типи корисного навантаження мають відхилятися без зміни довіреного стану та без переходу на відкритий текст.

Статус незалежного аудиту протоколу залишається **CHANGES REQUIRED**. Не презентуйте експериментальну поведінку форку як остаточно підтверджене криптографічне рішення.

## Модель гілок та робочий процес (Branching Workflow)

Для розробки застосовується структурована модель життєвого циклу гілок:

```
feature/<назва-фічі>    ──┐
feature/<назва-фіксу>   ──┼──>  [ dev ]  ──>  [ main ]  (релізні теги v12.10.5)
```

1. **Активна розробка у `dev`**:
   - Головною гілкою для щоденної інтеграції є **`dev`**.
   - Прямі коміти в `main` заборонені.
2. **Гілки завдань (`feature/<назва>`)**:
   - Нові можливості та виправлення помилок створюються окремими гілками від `dev`: `git checkout -b feature/моя-фіча dev`.
   - Використовуйте атомарні коміти у форматі Conventional Commits (`feat(secure): ...`, `fix(android): ...`, `test(secure): ...`, `docs: ...`).
3. **Pull Requests та злиття**:
   - Усі Pull Request відкриваються виключно в гілку **`dev`**.
   - Злиття в `dev` відбувається лише після успішної збірки та проходження локальних тестів.
4. **Релізи**:
   - Релізні версії зливаються з `dev` у `main`.
   - Релізи позначаються версійними тегами (`v<version>`), що автоматично запускає складання multi-architecture APK у GitHub Actions CI.

## Вимоги до верифікації коду

Перед відправленням змін на перегляд переконайтеся у їх працездатності:

1. **Перевірка оточення та локальна збірка**:
   ```bash
   ./scripts/check-local-mvp.sh
   ./scripts/build-local-mvp.sh
   ```
2. **Перевірка компіляції**:
   ```bash
   nix-shell --run './gradlew :SecureOverlay:compileDebugAndroidTestJavaWithJavac :TMessagesProj:compileReleaseJavaWithJavac --console=plain'
   ```
3. **Інструментальні тести на пристрої**:
   Для будь-яких змін у криптографії, сховищах, кодеках чи стані ратчета запустіть інструментальні тести на підключеному телефоні:
   ```bash
   nix-shell --run 'ANDROID_SERIAL=<device_serial> ./gradlew :SecureOverlay:connectedDebugAndroidTest --console=plain'
   ```
4. **Тестування на двох пристроях**:
   Для змін у транспорті, UI чату чи передачі медіа проведіть ручну перевірку між двома реальними акаунтами та зафіксуйте результат.

## Правила комітів та гігієна безпеки

- Дотримуйтесь Conventional Commits: `feat(secure): ...`, `fix(android): ...`, `test(secure): ...`, `docs(security): ...`, `ci: ...`.
- Тримайте коміти логічними та компактними; не поєднуйте загальний рефакторинг зі змінами безпеки в одному коміті.
- **Ніколи не комітьте конфіденційні дані**: `local.properties`, API ключі Telegram, файли підпису (`keystore/`, `*.p12`), розшифровані медіафайли, логи чи персональні номери телефонів.
- Про виявлені вразливості повідомляйте приватно, як описано в [`SECURITY_UK.md`](SECURITY_UK.md).
