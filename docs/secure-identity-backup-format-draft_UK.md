# Формат резервної копії ідентичності Fork-Secure — чернетка 1

> [!NOTE]
> [The English version of this documentation is available in secure-identity-backup-format-draft.md](secure-identity-backup-format-draft.md).

**Статус:** реалізовано локальний MVP виключно для ідентичності (`FSBK`); незалежний огляд формату, крос-імплементаційні фікстури та деструктивні тести перевстановлення/відновлення залишаються обов'язковими перед використанням як офіційного механізму відновлення.
Ця чернетка визначає архів лише для безперервності ідентичності. Вона не зберігає відкритий текст повідомлень, маніфести вкладень, медіафайли, довіру до контактів, сесії, паролі Telegram, чернетки, логи чи дані сповіщень.

## Межа загроз та відновлення

Архів захищає від втрати однієї інсталяції, коли користувач зберігає як сам архів, так і пароль до нього. Викрадення обох дозволяє автономний підбір пароля (offline brute-force). Скомпрометований розблокований пристрій може експортувати ідентичність і перебуває поза межами захисту цього архіву.

Відновлення вимагає авторизації під тим самим Telegram ID власника та інсталяції без активних захищених чатів чи віддаленого стану протоколу. Воно може замінити автоматично згенеровану, але ще не використану локальну ідентичність; воно ніколи не перезаписує активну ідентичність без відома користувача.
Відновлення одного архіву на кількох пристроях створює клони; співрозмовники повинні виявляти це за допомогою протоколу відновлення, описаного нижче. Співрозмовник, який ніколи не бачив цієї ідентичності, не може самостійно виявити відновлений старий архів.

## Канонічний бінарний контейнер

Усі цілі числа мають порядок big-endian без знаку. Парсери відхиляють непідтримувані значення, ненульові зарезервовані поля, переповнення довжини, обрізання та зайві байти перед запуском KDF, де це можливо.

| Поле | Розмір | Обов'язкове значення |
| --- | ---: | --- |
| Magic | 4 | ASCII `FSBK` |
| Версія формату | 2 | `1` |
| KDF ID | 1 | `2` = PBKDF2-HMAC-SHA-256 |
| AEAD ID | 1 | `1` = AES-256-GCM |
| Прапорці (Flags) | 2 | `0` = захищено паролем, `1` = явно без захисту |
| Параметр KDF 1 | 4 | ітерації = `600000` |
| Параметр KDF 2 | 4 | `0` |
| Паралелізм KDF | 1 | `1` |
| Довжина солі | 1 | `16` |
| Довжина нонса | 1 | `12` |
| Зарезервовано | 1 | `0` |
| Довжина відкритого тексту | 4 | `1..4096` |
| Сіль | 16 | свіжі випадкові байти |
| Нонс | 12 | свіжі випадкові байти |
| Шифротекст | довжина відкритого тексту | результат AES-GCM без тегу |
| Тег автентифікації | 16 | тег AES-GCM |

`AAD` — це кожен байт від `Magic` до `Nonce` включно.
PBKDF2-HMAC-SHA-256 виводить рівно 32 байти з пароля UTF-8 та збереженої солі. Нормалізація пароля не виконується; при використанні пароля інтерфейс вимагає ідентичного введення двічі та щонайменше 5 символів, тоді як кодек приймає щонайбільше 512 байтів UTF-8. Порожній пароль приймається лише за наявності автентифікованого прапорця `1`; він виводиться з публічної константи і забезпечує цілісність, але не конфіденційність. Інтерфейс повинен показувати явне попередження перед створенням або імпортом такого файлу. Параметри KDF ID 2 відповідають рекомендаціям OWASP Password Storage Cheat Sheet.
Argon2id залишається пріоритетним майбутнім KDF ID після аудиту залежностей та тестів.

## Автентифікований відкритий текст

Розшифрований відкритий текст починається з ASCII `FSBP`, версії `U16 = 1`, далі слідують канонічні поля, закодовані як `tag U8 | length U16 | value`. Теги суворо зростають, є унікальними та повними; невідомі теги у версії 1 відхиляються.

| Тег | Значення |
| ---: | --- |
| 1 | випадковий ID архіву, рівно 16 байтів |
| 2 | Telegram ID власника, `U64`, ненульовий |
| 3 | покоління ідентичності, `U64` |
| 4 | Unix-час експорту, `U64` |
| 5 | реєстраційний ID libsignal, `U32` |
| 6 | серіалізована пара ключів ідентичності, `16..512` байтів |
| 7 | SHA-256 канонічного публічного ключа ідентичності, 32 байти |
| 8 | політика відновлення, `U8 = 1` (лише ідентичність) |

Імпорт виводить публічну ідентичність із тегу 6 та порівнює тег 7 за константний час. Реєстрація та серіалізація ключів також повинні пройти парсинг libsignal та валідацію діапазонів перед будь-якою зміною стану.

## Транзакція відновлення

1. Перевірити межі ресурсів, автентифікувати/розшифрувати, перевірити всі поля, порівняти поточний Telegram ID користувача та показати відновлений відбиток.
2. Відхилити, якщо стан захищених розмов, стан сесій/ідентичностей контактів, підготовлене відновлення або незавершений маркер уже існують. Помилка перевірки залишає весь стан незмінним.
3. Підготувати ідентичність та реєстрацію під окремими зашифрованими іменами записів та атомарно записати маркер відновлення `PREPARED`.
4. Після явного підтвердження користувачем атомарно замінити лише ідентичність та реєстрацію, видалити prekeys/довіру/сесії та встановити маркер `COMMITTING`.
5. Очистити всі бар'єри захищених чатів. Конструктор захищеного рушія ідемпотентно завершує імпорт у стані `COMMITTING` перед відкриттям стану надсилання/дешифрування.
6. Згенерувати свіжі prekeys, збільшити збережене покоління ідентичності, створити новий ID відновлення, після чого видалити маркер та тимчасові записи.

Зашифроване сховище блобів шифрує всі оновлення перед виконанням однієї синхронної транзакції налаштувань. Тимчасові дані та маркер шифруються в Keystore. Імпорт у стані `PREPARED` очікує явного підтвердження відбитка і може бути видалений без зміни стану протоколу; імпорт у стані `COMMITTING` завжди доводиться до кінця. Пароль і розшифровані тимчасові масиви байтів очищаються після обробки, а робота KDF виконується поза потоком інтерфейсу.

Локальний запис покоління відновлення та класифікатор відкату/клонування контактів реалізовані незалежно від імпорту архіву. Вони використовують зашифровані записи фіксованої довжини в Keystore, ніколи не змінюють довіру до контактів під час класифікації та просувають локальне покоління, коли користувач явно скидає свою ідентичність. Новий кодек спарювання версії 2 містить ці метадані, а його підпис ідентичності покриває канонічний pre-key бандл, покоління та recovery ID. Вища генерація ставить захищене надсилання на паузу до явного підтвердження у діалозі відновлення; відкат, клон того самого покоління та пропозиції даунгрейду відхиляються без заміни довіреної сесії.

Інтерфейс Android відображає глобальну ідентичність, покоління, поточну кількість захищених станів, зашифрований експорт, поетапне відновлення та скидання ідентичності в `Налаштування > Fork-Secure`. Цей екран чітко зазначає, що архів не містить списку чатів/сесій. Після відновлення всі захищені бар'єри очищаються, і кожен контакт повинен пройти спарювання та верифікацію наново.

## Протокол відновлення контактів (Peer Recovery Protocol)

Наступний об'єкт спарювання повинен автентифікувати `identity_generation` та випадковий `recovery_id` під відновленою ідентичністю. Співрозмовник зберігає найвище прийняте покоління та recovery ID:

- нижче покоління: відхилити як спробу відкату (rollback);
- те саме покоління та однаковий recovery ID: ідемпотентний дублікат;
- те саме покоління та інший recovery ID: заблокувати як можливий клон;
- вище покоління: показати подію відновлення, призупинити захищене листування та вимагати явної повторної верифікації перед прийняттям нових сесій.

Оригінальний активний пристрій стає застарілим після того, як співрозмовники приймуть вище покоління. Цей механізм обмежує виявлення клонів/відкатів тими співрозмовниками, які раніше зберегли стан ідентичності; це не є глобальним реєстром пристроїв.

## Необхідні фікстури та приймання

Перед релізним використанням мають бути опубліковані машиночитані тестові вектори для контейнера, KDF, AEAD та кодування відкритого тексту, а також негативні тести для невірного пароля, підробки, некоректних довжин, зайвих байтів, невідповідності акаунта, розбіжності ключів/відбитка, відкату, повторного відновлення та клонування. Два незалежні тестові споживачі повинні відтворити їх.

Приймання також вимагає тестів переривання відновлення на кожній фазі маркера, тестів перевстановлення та відновлення на двох телефонах, підтвердження того, що резервне копіювання Android/Telegram виключає всі налаштування Fork-Secure, і доказів того, що тимчасові буфери відкритого тексту та паролів не зберігаються на диску та не потрапляють у логи.

## Планований автоматичний архів відновлення

Архів лише для ідентичності `FSBK` не може відновити доступ до минулих захищених повідомлень або вкладень. Окрема автоматична ревізія архіву (за бажанням користувача) повинна покривати ідентичність разом із локальними записами відображення та автентифікованими маніфестами медіа/ключами контенту. Вона не повинна відновлювати знімок живого ратчета/сесій: відкат стану відправлення назад може призвести до повторного використання ключів повідомлень. Відновлені контакти залишаються на паузі до нового спарювання та верифікації. Хмарний провайдер повинен отримувати лише автентифікований шифротекст архіву, ніколи не отримуючи відкритих повідомлень, розшифрованих медіа, паролів, облікових даних Telegram чи «сирих» ключів Keystore.
