# Telegram Secure overlay protocol v1 — review draft

**Status:** design draft; **not approved for implementation or release**.
**Scope:** verified 1:1 UTF-8 text between one Android device per participant.
**Transport:** ordinary Telegram messages carry opaque protocol envelopes. Telegram and official clients remain protocol-compatible but cannot read secure content.

This document is the implementation gate for the secure overlay. It replaces the local symmetric-key demo design; it does not modify MTProto, Telegram server behavior or upstream Telegram message semantics.

## 1. Security goals and limits

After authenticated setup, the protocol aims to provide confidentiality, integrity, peer/device authentication, replay resistance, forward secrecy and explicit downgrade detection for supported clients.

It does not hide Telegram account identities, peers, timestamps, approximate carrier size, message frequency, IP/network metadata, push timing, screenshots, compromised endpoints or intentional recipient disclosure.

Secure mode is opt-in per peer. The client must present distinct normal, secure-pending, secure-active, key-changed, session-invalid and error states. No secure failure may be rendered as normal plaintext.

## 2. Preconditions and terminology

- **Telegram peer binding:** the authenticated Telegram account/chat context supplied by the fork, never a user ID merely claimed inside a carrier.
- **Device:** a stable, opaque protocol device ID generated by the client; it is not a hardware identifier.
- **Identity bundle:** versioned public device material: owner Telegram user ID, device ID, Ed25519 signing key, X25519 agreement key, key version, creation/expiry data and a signature by the signing key over canonical bundle bytes.
- **Verified identity:** an identity bundle that the user explicitly compared/verified and that is bound to the current Telegram peer.
- **Session:** a peer-device-pair state established after mutual authentication and confirmation.
- **Carrier:** a Telegram text message whose content begins with the reserved secure marker and contains one canonical encoded protocol envelope.

All fields use a specified canonical binary encoding selected during review. Text parsing and delimiter-separated state are prohibited. Every decoder validates a total carrier limit, decoded-envelope limit and individual field limits before allocating nested objects.

## 3. Cryptographic profile

The profile is provisional until external review fixes library and parameter choices.

- Identity signatures: Ed25519.
- Agreement keys: X25519.
- KDF: HKDF-SHA-256 with explicit, protocol-versioned labels and transcript binding.
- Payload AEAD: XChaCha20-Poly1305 with a fresh 24-byte random nonce per encryption.
- Randomness: Android/Java cryptographic secure random source.
- Post-setup ratchet: maintained, audited Signal Double Ratchet implementation; no custom ratchet built from these primitives.

Keys are separated by purpose. Identity signing keys must not be used as X25519 agreement keys. A protocol-version or cipher-suite transition is an authenticated state transition, never a best-effort fallback.

## 4. Identity, device and trust lifecycle

1. On first use, create a per-device Ed25519 signing identity and X25519 agreement identity according to the Android Keystore policy.
2. Construct and self-sign an identity bundle in canonical bytes.
3. Exchange identity bundles only through a user-initiated capability/session flow in the verified Telegram peer chat.
4. Verify the bundle signature, exact Telegram peer binding, device ID validity, protocol version and expiry before trust UI is offered.
5. The user verifies a fingerprint/QR derived from both canonical bundles and the handshake transcript. Only this action creates `verified` trust.
6. A changed key, unknown device, expired bundle, Keystore reset or corrupted state invalidates affected sessions and blocks secure sending until explicit review.

Trust records are keyed by Telegram user ID **and** device ID. A key change cannot overwrite a previously verified record or silently continue a session.

## 5. Capability and setup state machine

Capability discovery is user initiated and per-peer rate limited. Cache entries have a short explicit expiry and are advisory only; they never authorize encryption by themselves.

`normal -> capability-requested -> capability-confirmed -> identity-pending -> verified -> session-establishing -> secure-active`

Terminal/security states:

- `key-changed`, `device-changed`, `session-invalid`, `unsupported-version`, `authentication-failed`, `storage-failed`, `keystore-failed`.

All terminal/security states block secure sending. A UI action may return to `normal` only after a clear warning; it must not send the typed secure draft as normal text automatically.

## 6. Authenticated setup requirements

The final reviewed handshake must use fresh X25519 ephemeral keys and authenticate both roles with their Ed25519 identity keys. It must include:

- both canonical identity bundles and exact Telegram peer/device bindings;
- protocol version and selected cipher suite;
- initiator/responder role labels;
- both ephemeral public keys;
- a transcript hash over all prior canonical setup messages;
- explicit key confirmation before `secure-active`;
- unique session ID and key version;
- expiry/retry rules and per-peer rate limits.

HKDF inputs must be specified exactly, including salt, input key material, labels and output key separation. The handshake specification and test vectors require independent cryptographic review before code is accepted.

## 7. Secure message envelope requirements

The final envelope version must contain, in canonical encoded fields:

- magic/version and message type;
- sender and recipient Telegram user IDs and protocol device IDs;
- session ID, ratchet/key ID and message number;
- nonce and ciphertext/tag;
- any ratchet header required by the selected audited implementation.

AEAD associated data authenticates every cleartext routing/security field above, plus the negotiated suite and transcript/session binding. Payload plaintext is valid UTF-8 with a documented maximum size.

An unknown version, malformed field, invalid length, wrong peer/device/session, duplicate, expired session or AEAD failure is a **rejected secure message**. It must be visible as such in a secure chat; it must never become `IncomingPlainText`.

## 8. Replay, ordering and durable state

Authentication occurs before replay-state mutation. After AEAD authentication succeeds, the client atomically persists the ratchet/replay transition before showing content. Sending similarly uses a durable counter/ratchet transition before transport submission, with an explicit recovery state if submission outcome is uncertain.

The selected ratchet implementation defines a bounded skipped-message/replay policy. Persisting an unbounded set of all received message numbers is prohibited. State storage must be versioned, authenticated, crash-safe and recoverable; decode/corruption failures preserve a visible security-reset record.

## 9. Local data and UX rules

- Identity and wrapping keys use the documented Keystore policy; key invalidation is a security event, not an opportunity to silently create a replacement session.
- Secure plaintext must not enter Telegram message bodies, notification content, crash logs, analytics, drafts, previews or plaintext caches.
- Secure notifications use generic text only. Screenshot/app-switcher/clipboard/accessibility behavior is explicit product policy and is tested on physical devices.
- Android backup is disabled for secure state. Any future recovery backup is opt-in and separately specified with passphrase KDF, AEAD, rollback protection and migration rules.

## 10. Required verification before implementation approval

1. External cryptographic review of this completed specification and the chosen ratchet/library.
2. Published test vectors for identity bundles, capability messages, handshake transcript/KDF and encrypted envelopes.
3. Two independent client interoperability tests using two isolated Telegram accounts.
4. Fuzzing of every carrier/state decoder with enforced resource bounds.
5. Regression tests for invalid AEAD without replay consumption, downgrade, key/device change, corrupt/rolled-back persistence and Keystore invalidation.
6. A documented compatibility policy for official clients and unsupported Telegram Secure versions.

Until all of these pass, this document authorizes no claim of end-to-end security and no confidential-user beta.
