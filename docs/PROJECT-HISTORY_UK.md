# Журнал історії проєкту Telegram Secure

> [!NOTE]
> [The English version of this documentation is available in PROJECT-HISTORY.md](PROJECT-HISTORY.md).

Цей журнал фіксує ключові рішення проєкту, пов'язані з безпекою, та підтверджувальні артефакти. Основним джерелом істини залишається історія Git та актуальна документація; цей журнал не надає повноважень на зміну реалізації.

## 2026-08-11 — ітерація закритої бети та аудит продуктивності

**Подія:** Функціональність Fork-Secure була доопрацьована у форку клієнта Telegram для тестування на двох фізичних пристроях: захищене відображення 1:1 тексту та медіафайлів, режим «Збережені повідомлення», інтерфейс відновлення, локальний зашифрований кеш медіа та інтеграція переглядача/списків у стилі Telegram.

**Фактичні результати (Runtime):** Профілювання на пристрої RMX3491 з обмеженою пам'яттю виявило завантаження холодної історії захищеного чату в потоці інтерфейсу (UI thread). Цільовий попередній прогрів рушія (`engine prewarm`) зменшив виміряний час конструювання в основному потоці приблизно зі 176 мс до ~1 мс. Додаткові маркери трасування тепер розділяють прогрів рушія, початковий та кешований оверлей, збережені повідомлення, відповіді та процес спарювання. Залишкові затримки історії все ще перебувають під аудитом; жоден маркер продуктивності не містить відкритого тексту, ключів, даних носіїв чи ідентифікаторів контактів.

**Статус безпеки:** Статус незалежного криптографічного аудиту залишається `CHANGES REQUIRED`. Локальні збірки та ручні перевірки на пристроях демонструють поведінку інтерфейсу, але не замінюють формального схвалення криптографії чи гарантій промислової безпеки.

## 2026-07-21 — фіксація базового протоколу для аудиту

**Подія:** Зафіксовано базовий апстрім-коміт клієнта Telegram `9bcf3d2769c6d3f07105a992e5d9493e33ac3348` (`оновлення до 12.9.0 (6966)`) та підготовлено специфікацію **Telegram Secure overlay protocol v1, revision 1** для незалежного криптографічного огляду.

**Рішення:** `CHANGES REQUIRED`. Це базова лінія виключно для рев'ю. Жодна промислова криптографія, парсер носіїв, довговічне сховище стану, адаптер Telegram чи захищений UI не авторизовані.

**Артефакти та підтвердження:**

- [Запис форку](../FORK_UK.md) та фіксація апстріму вище.
- [Запит на аудит](protocol-review/REVIEW-REQUEST.md), [шаблон рішення](protocol-review/REVIEW-DECISION.md), [контрольний список](protocol-review/REVIEW-CHECKLIST.md), [покриття фікстурами](protocol-review/FIXTURE-COVERAGE.md) та [блокуючі питання](protocol-review/OPEN-ISSUES.md).
- Точні байти зафіксовано контрольними сумами в [REVIEW-ARTIFACTS.sha256](protocol-review/REVIEW-ARTIFACTS.sha256); процедура передачі та верифікації описана в [REVIEW-HANDOFF.md](protocol-review/REVIEW-HANDOFF.md).
- Попередня локальна валідація батьківської пісочниці не змогла відтворити збірку Nix: для дозволу `<nixpkgs>` був потрібен реєстр Nix flake, але мережевий доступ був відсутній; прямий запуск Gradle також не мав JDK у `PATH`. Це свідчення середовища, а не результати тестів коду (див. [`../../SECURITY_READINESS_AUDIT_UK.md`](../../SECURITY_READINESS_AUDIT_UK.md), «Test and build evidence»).
- Ізольована команда збірки форку `SecureOverlay` (`nix-shell --run './gradlew :SecureOverlay:assembleDebug :SecureOverlay:testDebugUnitTest --console=plain'`) успішно виконана 2026-07-21 на JDK 17 після отримання доступу до локального демона Nix. Вона не містила модульних тестів (`NO-SOURCE`); це базовий результат компіляції, а не підтвердження безпеки протоколу чи інтероперабельності.

**Блокуючі проблеми:** зазначений та зафіксований бекенд Signal Double Ratchet і межі адаптера; незалежне рев'ю handshake/CFS/лімітів/міток; автентифіковане походження співрозмовника/чату Telegram та межі надійної відправки; політика скидання/відкату/пошкодження Keystore; повні незалежно відтворювані вектори з двома споживачами; юридичне та продуктове схвалення маркера носія та поведінки захищеного/резервного UX. Офіційний перелік міститься в [OPEN-ISSUES.md](protocol-review/OPEN-ISSUES.md).

**Чинний шлюз:** `CHANGES REQUIRED` у [REVIEW-DECISION.md](protocol-review/REVIEW-DECISION.md).

**Наступний зовнішній крок:** надати зафіксований маніфестом пакет незалежному криптографічному аудитору та отримати письмове рішення. Лише явне схвалення `APPROVED`, яке закриває кожну блокуючу проблему, може відкрити фазу повноцінної ізольованої реалізації.
