# Аудит безпеки можливостей Telegram Fork-Secure

> [!NOTE]
> [The English version of this documentation is available in fork-secure-feature-security-audit.md](fork-secure-feature-security-audit.md).

**Дата аудиту:** 2026-10-01  
**Область аудиту:** звичайні 1:1 хмарні чати у приватному форку для Android. Нативні Secret Chats та групові чати Telegram не змінюються.

## Загальний підсумок

Поточна кодова база містить повністю функціональний прототип шифрування тексту, фото, відео, аудіо, документів, контактів, геопозиції та стікерів із централізованим бар'єром fail-closed для вихідних дій. Непідтримувані дії блокуються до відправлення на сервери Telegram.

Сервери Telegram продовжують бачити ідентифікатори обох акаунтів, точний час відправлення повідомлень і файлів, розміри зашифрованих носіїв, статус доставки/прочитання та мережеві IP-дані. Fork-Secure не може приховати ці властивості при використанні інфраструктури Telegram.

## Стан реалізації можливостей

| Можливість | Поточний стан реалізації | Залишкові витоки метаданих або обмеження |
| --- | --- | --- |
| Текст | Зашифрований носій `TGS1:`; локальний кеш відображення | Telegram бачить розмір та час відправлення |
| Відповіді та цитати | Зашифроване тіло; незашифровані поля цитат очищуються | ID повідомлення відповіді залишається метаданими Telegram |
| Пересилання | Захищений текст та медіа (фото, голос, відео, аудіо, файли) розшифровуються локально та шифруються повторно для цільової сесії зі збереженням вигляду | Отримувач має бути захищеним контактом або сесією Saved Messages |
| Безшумне надсилання | Прапорець `notify=false` зберігається | Сервер Telegram бачить прапорець безшумного надсилання |
| Відкладене надсилання | Зашифрований носій та розклад зберігаються | Telegram бачить запланований час надсилання |
| Стікери | Байти WEBP, TGS та WEBM шифруються з випадковими іменами | Розмір файлу та час залишаються видимими |
| Фото та переглядач | Оригінальні байти, ім'я, MIME та підпис шифруються; переглядач та альбоми працюють; примусовий `FLAG_SECURE`; експорт/поширення заблоковано | Спойлери та одноразові медіа ще в розробці |
| Документи та аудіо/голос | Байти, автентифіковані метадані, аудіохвиля, назва/виконавець зашифровані; нативне відтворення прямо з розшифрованого кешу | Стримінг для багатогігабайтних файлів |
| Редагування | Зашифроване повідомлення керування редагуванням із локальним відкатом | Захист від replay та історія редагувань у кеші |
| Реакції | Заблоковано fail-closed для захищених чатів та носіїв Fork-Secure | Незашифровані хмарні реакції відхиляються з повідомленням користувачу |
| Видалення | Автентифікований пакет дистанційного видалення Signal очищує текст, контент та файли на диску за дайджестом | Telegram синхронізує видалення носія; затримка доставки видалення, якщо співрозмовник офлайн |
| Контакти | Зашифрований корисний вантаж `TYPE_CONTACT` у носії; відкриті дані vCard очищуються | Telegram бачить лише розмір зашифрованого носія |
| Геопозиція | Зашифрований корисний вантаж `TYPE_GEO_LOCATION`; прев'ю блокує зовнішні запити до тайлів карт (`currentMapProvider = -1`), відкривається у секретному режимі | Telegram бачить лише розмір носія; потрібна згода користувача на показ карти |
| Захист екрана | `FLAG_SECURE` активний у `ChatActivity`, `ProfileActivity`, `ChatMessageCell` та `PhotoViewer`; експорт до галереї та поширення заблоковані | Root/OS-хуки за межами віконної безпеки Android |
| Посилання та анти-фішинг | Клієнтське розпізнавання посилань; `SecureLinkGuard` виявляє IDN/омогліфи, Punycode, невидимі символи та спуфінг authority; обов'язкове підтвердження з канонічним URL перед відкриттям зовнішнього браузера | IP-адреса та метадані пристрою видимі сайту після відкриття |
| Скидання ідентичності та відновлення | Скидання, архів лише ідентичності та прототип ручного архіву ідентичності з історією | Відновлення історії ставить на паузу всі чати; автоматичний бекап та безпечний мультидевайс у розробці |

## Закриті P0-шляхи витоку даних

1. Хмарні чернетки придушуються й не зберігаються під час активного захисту чату.
2. Серверний збір попереднього перегляду посилань (link previews) та веб-метадані повністю вимкнені.
3. Відкритий текст цитат та інші поля відповідей повністю вирізаються.
4. Централізований бар'єр вихідних повідомлень блокує будь-які недозволені дії. Нешифровані реакції відхиляються.
5. Видалення повідомлення або діалогу в Telegram очищує відповідні записи з локального кешу та диска; кеші обмежені за розміром.

## Матриця можливостей Telegram

### Можуть бути захищені поточною моделлю 1:1

- Форматований текст, сутності, підписи та клієнтські прев'ю посилань;
- Фотографії, відео, GIF, голосові повідомлення, круглі відеонотатки, аудіо та довільні файли;
- Контакти, статична геопозиція та заклади (venues) як автентифіковане корисне навантаження;
- Пересилання через локальне розшифрування та шифрування під сесію отримувача;
- Відповіді та цитати із зашифрованим текстом цитати;
- Заплановані та безшумні повідомлення;
- Автентифіковані службові пакети редагування, видалення та закінчення терміну дії.

### Потребують окремого протоколу стану

- Одноразові медіа (view-once) та підтвердження видалення;
- Оновлення геопозиції в реальному часі (live location);
- Опитування, голосування та списки завдань;
- Мультидевайс (fanout), видалення пристроїв та детекція клонування ідентичності;
- Наскрізне шифрування груп за схемою Sender Keys (поза межами цього аудиту).

### Не можуть залишатися конфіденційними при збереженні серверного функціоналу

- Хмарні чернетки, серверні прев'ю посилань, серверний переклад та серверний пошук по тексту;
- Боти, інлайн-боти, бізнес-боти, Mini Apps, ігри та платежі, які повинні обробляти вхідні дані;
- Публічні історії, розіграші та статистика каналів;
- Виявлення контактів, онлайн-статус, індикатор набору тексту та метадані доставки.

Правильна поведінка у захищеному режимі — вимикати ці функції або вимагати явного виходу із захищеного режиму.

### Вже захищені іншими межами безпеки Telegram

Telegram документує голосові та відеодзвінки 1:1 як наскрізно зашифровані (E2EE). Telegram Passport та нативні Secret Chats також мають власні окремі контури шифрування. Fork-Secure не повинен підміняти або неявно змінювати їх; він лише покращує верифікацію та пояснення конфіденційності в інтерфейсі.

Посилання: [Telegram APIs](https://core.telegram.org/), [типи MessageMedia](https://core.telegram.org/type/messagemedia), [хмарні чернетки](https://core.telegram.org/api/drafts), [заплановані повідомлення](https://core.telegram.org/api/scheduled-messages), [E2E дзвінки](https://core.telegram.org/api/end-to-end/video-calls), та [Telegram FAQ](https://www.telegram.org/faq).

## Поетапний план посилення безпеки (Hardening Plan)

1. Єдиний бар'єр вихідної політики для кожного захищеного чату 1:1. Дозволені лише перевірені носії тексту, стікерів, фото та документів.
2. Вимкнення синхронізації хмарних чернеток, серверних прев'ю посилань, відкритих цитат, дій ботів та непідтримуваних медіа під час захисту.
3. Прив'язка локальних записів кешу до ID повідомлень Telegram та їхнє видалення при видаленні carrier, виході з облікового запису, скиданні ідентичності та лімітах зберігання.
4. Завершення тестування перевстановлення та відновлення для архівів ідентичності та повної історії на фізичних пристроях. Відновлення історії повинно ставити контакти на паузу, а не відновлювати живі ратчети.
5. Почергове додавання нативних типів: відео, голосові нотатки, круглі відео, GIF та аудіо.
6. Впровадження автентифікованих протоколів редагування/видалення/реакцій/строку дії та тестів на конфлікти.
7. Аудит сповіщень, віджетів, буфера обміну, скріншотів, поширення/експорту, доступності (accessibility), логів, краш-репортів та тимчасових файлів на обох пристроях.

## Відкладений беклог конфіденційності та стійкості

Ці ідеї заплановані після завершення поточних етапів відновлення та медіа. Вони не є частиною базового протоколу повідомлень і не повинні затримувати запуск MVP для чатів 1:1.

### Заплановані кандидати

1. Додавання чек-листа безпеки та конфіденційності для Telegram 2FA, ризикованих налаштувань приватності, налагодження через USB та попереджень про цілісність пристрою. Усі зміни повинні бути явними та індивідуально перевірятися користувачем.
2. Перевірка працездатності проксі та опціональна ротація як функція транспорту Telegram. Вона повинна залишатися незалежною від `SecureOverlay`, зберігати обрану політику маршрутизації та ніколи автоматично не перемикатися на відкрите пряме з'єднання.
3. [Виконано] Пряма перевірка спуфінгу посилань на межі відкриття URL через `SecureLinkGuard` (Punycode, омогліфи, невидимі/BiDi-символи, спуфінг authority та цільових доменів).
4. Оцінка локальної зашифрованої бази даних після стабілізації життєвого циклу відновлення історії (SQLCipher/Keystore).
5. Профілі примусу (duress profiles) та хибний пароль виключно як окремо аудійована функція безпеки. Дії потребують надійного стану `pending/completed/failed` та автентифікованої активації через довірений контакт.

Модифікація голосу, маскування вигляду додатка та фотозйомка камерою при невірному паролі залишаються виключно дослідницькими ідеями. Вони несуть значні ризики для продуктивності та стабільності й не входять до найближчих планів.

### Архітектурні вимоги до інтеграції

- Зберігати протокол безпеки, транспорт Telegram, локальний захист даних та загальний інтерфейс конфіденційності в окремих пакетах із вузькими адаптерними інтерфейсами.
- Політика захищеного чату повинна залишатися єдиним бар'єром fail-closed для надсилання повідомлень; майбутні функції можуть спиратися на неї, але не повинні обходити її.
- Архіви відновлення повинні бути версіонованими та типізованими, щоб майбутній хмарний провайдер отримував лише автентифікований шифротекст.
- Деструктивні захисні дії не повинні змішуватися з транзакціями ратчета/сесій і мають бути ідемпотентними.
- Кожна нова можливість додається через цільові тести RED/GREEN та прапорці конфігурації перед увімкненням у закритій беті.

## Критерії приймання MVP (Acceptance Boundary)

Інтерфейс не повинен показувати захисний щит, якщо будь-яка видима дія надсилання може передати контент незашифрованим шляхом Telegram. Кожна непідтримувана дія повинна блокуватися з локалізованим поясненням. Мережеві тести та тести бази даних повинні доводити, що Telegram отримує лише непрозорі зашифровані носії/файли для кожної дозволеної дії, а відхилені дії не викликають передачі в мережу та не змінюють стан безпеки.
