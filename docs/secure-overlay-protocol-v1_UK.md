# Протокол захищеного оверлею Telegram v1 — специфікація для рев'ю

> [!NOTE]
> [The English version of this documentation is available in secure-overlay-protocol-v1.md](secure-overlay-protocol-v1.md).

**Статус:** ТІЛЬКИ ДЛЯ РЕВ'Ю — `changes required` до моменту отримання письмового підтвердження від незалежного аудитора у `protocol-review/REVIEW-DECISION.md`.

Цей документ визначає вимоги до MVP: один верифікований пристрій Android на користувача Telegram та наскрізне шифрування 1:1 UTF-8 тексту. Специфікація описує оверлей корисного навантаження додатку; вона не змінює MTProto, семантику TDLib, маршрутизацію або звичайні повідомлення Telegram. Файли, медіа, групи, мультидевайс, синхронізація історії, бекапи та міжплатформні клієнти перебувають поза межами цієї специфікації.

Нормативні терміни **MUST**, **MUST NOT**, **SHOULD** та **MAY** використовуються згідно з RFC 2119. Декодер ПОВИНЕН відхиляти, а не намагатися виправити неканонічні вхідні дані.

## 1. Профіль та криптографічні обмеження

`protocol_version = 1`; набір криптографічних алгоритмів `suite_id = 0x0001` визначає комбінацію:
`Ed25519 + X25519 + HKDF-SHA-256 + XChaCha20-Poly1305 + схвалений аудитором Signal Double Ratchet`. Жодні інші алгоритми у v1 не підтримуються. Непідтримуване значення повертає `UNSUPPORTED_VERSION` або `UNSUPPORTED_SUITE` і ніколи не переходить на відкритий текст.

| Параметр | Максимальний або точний розмір |
|---|---:|
| Байти UTF-8 носія Telegram, включаючи префікс | 8,192 |
| Текст конверта Base64url після `TGS1:` | 8,187 |
| Розкодований конверт | 6,144 байтів |
| Будь-яке службове навантаження | 2,048 байтів |
| Зашифрований відкритий текст UTF-8 | 4,096 байтів |
| ID пристрою / ID сесії | Рівно 16 байтів |
| Публічний ключ Ed25519 / X25519 | Рівно 32 байти |
| Підпис Ed25519 | Рівно 64 байти |
| Нонс XChaCha / тег AEAD | Рівно 24 / 16 байтів |
| Номер повідомлення ратчета / довжина попереднього ланцюга | 0…2^32-1 |
| Збережені пропущені ключі / допустимий розрив ланцюга | 256 / 256 |
| Валідність бандла / тривалість життя сесії | 90 днів / 30 днів або 65,536 повідомлень |

Усі часові мітки задаються у беззнакових секундах Unix. Бандл приймається тільки якщо `created_at <= now + 300` та `now <= expires_at`; сесія приймається лише коли `now <= expires_at`. Збій системного годинника або стрибок назад понад 300 секунд блокує роботу зі статусом `CLOCK_UNTRUSTED`.

## 2. Канонічне бінарне кодування (CFS)

Кожен бінарний об'єкт є канонічною послідовністю полів (**Canonical Field Sequence — CFS**):

```
object := magic[4] || version:u8 || type:u8 || fields
field  := tag:u8 || length:u16be || value[length]
```

Поля розташовані у суворо зростаючому порядку тегів, зустрічаються рівно один раз і мають фіксовані мінімальні розміри. Невідомі поля, надлишкові байти, невизначені представлення чисел, дублікати або неканонічний текст призводять до відхилення пакета. Цілі числа кодуються у форматі unsigned big-endian; текст має бути найкоротшим валідним UTF-8 без нульових байтів (NUL) і ніколи не нормалізується. Перевіряйте ліміти носія та декодованих байтів перед виділенням Base64, а потім ліміти об'єкта перед розбором.

Носій Telegram містить маркер `TGS1:` плюс RFC 4648 base64url без вирівнювання (`=`) для одного CFS-конверта. Маркер зарезервовано: текст, що починається з нього, вважається захищеним носієм навіть у разі пошкодження, і ПОВИНЕН відображатися як явна помилка замість звичайного тексту у налаштованому або очікуваному захищеному чаті.

Загальні значення: `U64` = 8 байтів; `U32` = 4 байти; `ID` = 16 байтів; `KEY` = 32 байти; `SIG` = 64 байти; `HASH` = 32 байти. Ідентифікатори користувачів Telegram — позитивні `U64`; ID пристроїв — рівномірно випадкові непрозорі ID (ніколи не апаратні ID).

## 3. Реєстр об'єктів

| Тип | Magic/тип | Обов'язкові поля CFS (тег: значення) |
|---|---|---|
| identity bundle | `TGSB/0x01` | 1 suite U16, 2 owner U64, 3 device ID, 4 key version U32, 5 created U64, 6 expires U64, 7 Ed key KEY, 8 X key KEY, 9 rotation HASH або порожньо, 10 signature SIG |
| capability request | `TGSC/0x01` | 1 request ID, 2 initiator bundle bytes, 3 target owner U64, 4 target device ID, 5 issued U64, 6 expires U64 |
| capability response | `TGSC/0x02` | 1 request ID, 2 responder bundle bytes, 3 initiator owner U64, 4 initiator device ID, 5 issued U64, 6 expires U64, 7 signature SIG |
| handshake init | `TGSH/0x01` | 1 handshake ID, 2 initiator bundle bytes, 3 responder bundle hash HASH, 4 initiator ephemeral KEY, 5 issued U64, 6 expires U64, 7 signature SIG |
| handshake response | `TGSH/0x02` | 1 handshake ID, 2 responder bundle bytes, 3 init hash HASH, 4 responder ephemeral KEY, 5 issued U64, 6 expires U64, 7 transcript HASH, 8 signature SIG |
| handshake confirm | `TGSH/0x03` | 1 handshake ID, 2 role (`0x49` I або `0x52` R), 3 transcript HASH, 4 confirmation 32 bytes |
| secure envelope | `TGSE/0x01` | §6 |

Для підписаного об'єкта поле підпису (включаючи тег і довжину) пропускається для отримання `signed_bytes`; `signature = Ed25519.Sign(signing_secret, SHA-256("TGS/v1/sign" || signed_bytes))`. Ротація бандла порожня лише для першої ідентичності; інакше вона містить SHA-256 попереднього верифікованого бандла CFS та інвалідує старі сесії. Підпис відповіді створюється ключем ідентичності респондера.

## 4. Сумісність можливостей та довіра (Capability & Trust)

Користувач явно ініціює виявлення для одного звичайного 1:1 співрозмовника Telegram. Адаптер, а не вміст носія, надає автентифікованого відправника та чат; вони ПОВИННІ збігатися з власником бандла та обраним контактом. Відправляється один запит на контакт за 10 хвилин, щонайбільше три за 24 години. `expires - issued <= 600`. Відповідь приймається лише для активного ID запиту в тому самому чаті до завершення терміну дії, після верифікації підписів бандла та відповіді. Кеш сумісності діє не більше 24 годин і ніколи не є згодою або довірою.

Перед початком сесії інтерфейс порівнює відбитки/QR, згенеровані як `base64url(SHA-256("TGS/v1/verify" || min(bundleA,bundleB) || max(bundleA,bundleB)))`. Лише успішне порівняння створює стан `VERIFIED`. Змінений або новий пристрій, прострочений бандл, скидання чи пошкоджений локальний стан блокують захищене використання і не можуть перезаписати попередній верифікований запис.

## 5. Автентифіковане рукостискання (Handshake)

Ролі фіксуються запитом: ініціатор I та респондер R. Обидва використовують верифіковані бандли та свіжі ефемерні ключі X25519. Запит init діє 10 хвилин і є одноразовим. Нульовий результат X25519, повторно використаний ID, невідповідний хеш бандла, невалідний підпис, неправильний контакт/чат/роль, застаріла часова мітка або невідповідність транскрипту відхиляються.

`init_signature` підписує `SHA-256("TGS/v1/hs-init" || init signed_bytes)`; `response_signature` підписує `SHA-256("TGS/v1/hs-resp" || response signed_bytes)`. Визначаємо `T0 = SHA-256("TGS/v1/transcript/0" || init_full_cfs)` та `T = SHA-256("TGS/v1/transcript/1" || T0 || response_full_cfs)`; поле transcript у відповіді дорівнює T.

Нехай SI/SR будуть публічними ключами ідентичності X25519, а EI/ER — ефемерними публічними ключами. Конкатенуйте в точному порядку:

```
IKM = X25519(eI, SR) || X25519(SI, eR) || X25519(eI, eR) || X25519(SI, SR)
salt = SHA-256("TGS/v1/hs-salt" || T)
PRK  = HKDF-Extract(SHA-256, salt, IKM)
root_key      = HKDF-Expand(PRK, "TGS/v1/root" || T, 32)
confirm_I_key = HKDF-Expand(PRK, "TGS/v1/confirm/I" || T, 32)
confirm_R_key = HKDF-Expand(PRK, "TGS/v1/confirm/R" || T, 32)
session_id    = first16(SHA-256("TGS/v1/session" || T))
```

`confirmation = HMAC-SHA-256(confirm_<role>_key, "TGS/v1/confirm" || role || handshake_id || session_id || T)`. I відправляє підтвердження після перевірки відповіді; R перевіряє, надійно створює сесію, потім підтверджує; I перевіряє та надійно зберігає сесію. До цього моменту жодна зі сторін не є `SECURE_ACTIVE`. `root_key` передається виключно у схвалений адаптер ратчета.

## 6. Межі Signal Double Ratchet та конверт повідомлення

Використовується підтримувана, незалежно перевірена бібліотека Signal Double Ratchet, схвалена аудитором. Адаптер приймає кореневий ключ (root key), роль I/R, ID сесії та прив'язку контакт-пристрій і видає непрозорий ключ повідомлення, публічний ключ ратчета (32), довжину попереднього ланцюга U32 та номер повідомлення U32. Він зберігає щонайбільше 256 пропущених ключів, відхиляє розриви понад 256, споживає ключ лише після успішного AEAD і дозволяє виключно одноразове використання. Код додатка НЕ ПОВИНЕН самостійно реалізовувати DH ратчета, KDF-ланцюги чи обробку пропущених ключів.

Поля `TGSE/0x01`: 1 suite U16; 2 sender owner U64; 3 sender device ID; 4 recipient owner U64; 5 recipient device ID; 6 session ID; 7 session expiry U64; 8 ratchet public KEY; 9 previous-chain U32; 10 message number U32; 11 nonce (24); 12 ciphertext-with-tag (17…4112). Відкритий текст — валідний UTF-8 від 1 до 4096 байтів. `AD = SHA-256("TGS/v1/envelope-ad" || envelope CFS з виключеними полями 11 та 12)`. Шифрування виконується через XChaCha20-Poly1305(message_key, nonce, plaintext, AD); поле 12 містить шифротекст і 16-байтний тег. Генеруйте свіжий випадковий нонс для кожного ключа повідомлення.

Перед AEAD перевіряйте походження контакту/чату, ідентичності, набір suite, ID сесії, строк дії та ліміти ресурсів. Не змінюйте стан replay/ратчета до успіху AEAD; атомарно зберігайте перехід перед показом відкритого тексту. При надсиланні зберігайте транзакцію до передачі в транспорт. Невизначений результат передачі — `SEND_OUTCOME_UNKNOWN`: блокуйте сесію та вимагайте явної зашифрованої ресинхронізації/скидання; ніколи автоматично не повторюйте з новим лічильником.

## 7. Довговічний стан, скидання та обробка помилок

Використовуйте версіоноване, автентифіковане, транзакційне сховище з монотонним `state_generation`; його ключ автентифікації захищений Android Keystore. Запис містить відбиток ідентичності, зв'язку контакт/пристрій, suite, строк дії, стан ратчета, ліміт пропущених ключів та покоління. Відкат, помилка розгортання ключа, збій автентифікації/декодування, відсутність ключа, апаратне скидання або невдала транзакція зберігають маркер скидання та блокують надсилання.

| Код | Обов'язковий результат |
|---|---|
| `NOT_SECURE_CARRIER` | Звичайний текст лише якщо маркер відсутній |
| `MALFORMED_CARRIER`, `RESOURCE_LIMIT`, `NON_CANONICAL` | Повідомлення про відхилення захищеного повідомлення; без змін стану |
| `UNSUPPORTED_VERSION`, `UNSUPPORTED_SUITE`, `DOWNGRADE_DETECTED` | Блокування; без переходу до відкритого тексту |
| `PEER_BINDING_FAILED`, `BUNDLE_INVALID`, `AUTH_FAILED` | Відхилення; без мутацій сесії |
| `REPLAY`, `OUT_OF_ORDER_LIMIT`, `SESSION_EXPIRED` | Відхилення та блокування/ресинхронізація за правилами |
| `STORAGE_FAILED`, `STORAGE_ROLLBACK`, `KEYSTORE_INVALIDATED`, `KEYSTORE_CORRUPT` | Постійне скидання безпеки |
| `SEND_OUTCOME_UNKNOWN`, `CLOCK_UNTRUSTED` | Блокування відправлення; явне ручне відновлення |

Єдиний можливий перехід на відкритий режим — це явне рішення користувача покинути захищений режим після попередження про блокування. Захищена чернетка видаляється; авто-відправлення відкритим текстом заборонене. Звичайне повідомлення Telegram під час активного захисту чітко позначається як незахищене і не може спричинити протокольний перехід.

## 8. Версіонування та криптографічний шлюз

Версія v1 приймає виключно цей точний набір magic/версія/тип/поля. Майбутні версії потребують нової версії, міграції, свіжих підписів та нового аудиту; заборонено перевизначати байти v1 або домовлятися про алгоритми через замовчування. Фікстури в `protocol-review/` є нормативними. Жодне рукостискання, ратчет, парсер носіїв, адаптер транспорту чи інтерфейс Telegram не авторизовані доти, доки рішення не набуде статусу `APPROVED` і кожне блокуюче питання не буде закрито письмово.
